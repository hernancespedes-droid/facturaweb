# 0.38.1 — La base se actualiza sola

## Qué incluye
- **Después de actualizar el código con GIT, el primer pedido aplica los cambios de base pendientes** (D-59). Ya no hace falta entrar a «Sistema → Aplicar cambios»
  en el master ni a «Aplicar cambios en todas» en el panel de clientes: cada instalación (master y cada cliente) se actualiza con las migraciones de su propia carpeta
  (`main` o `estable`), así un cliente nunca recibe un cambio de base de una versión que todavía no tiene.
- Un candado por base evita que migren dos pedidos a la vez; el otro ve «Actualizando el sistema» unos segundos y la pantalla se recarga sola.
- Si algo falla, **el sistema no se bloquea**: el Master ve el aviso en Sistema (con el detalle), `/salud` informa `migracion_error` y no se reintenta durante un minuto.
  Se arregla y se aprieta «Aplicar cambios» (el aviso se va).
- «Aplicar cambios» y «Aplicar cambios en todas» siguen estando, para adelantar o resolver a mano.
- Se rescató solo esto de la rama `claude/instalaciones-genericas`: su panel por `/salud`, perfiles de alta y canal `estable` ya los cubren la 0.28.0 y la 0.29.0.
- Arreglo de pruebas: en una base nueva el EFECTIVO de prueba no aceptaba vuelto y el recorrido del navegador fallaba.

## Qué probar (Master en oys.orgysis.site)
1. GIT → actualizar `facturador_web` y **no** entrar a Sistema: navegar normal. Después, Sistema → «La base está al día» y en la lista aparece `0030_sistema_estado.sql` aplicada.
2. `/salud` muestra `"cambios_de_base_pendientes":0` y `"migracion_error":false`.
3. Pasar a clientes y actualizar `facturador_clientes`: entrar a un cliente y ver en su Sistema que quedó al día sin apretar nada.

## Desplegar
GIT como siempre. La migración `0030_sistema_estado.sql` (crea la tabla `sistema_estado`) ya se aplica sola. Recomendado: backup de la base antes (phpMyAdmin → Exportar).

## Revertir
GIT a 0.29.0. La tabla `sistema_estado` queda y no molesta; se vuelve a usar «Aplicar cambios» a mano.
